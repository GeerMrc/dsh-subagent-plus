# 0004 — 产品线固定 0.0.x；0.3.0 为误发孤儿包；版本号只在发布时推进

日期：2026-10-29 ｜ 状态：用户裁定，立即生效 ｜ 取代：[0002](2026-10-29-takeover-v0.3.1-refinements.md) 决策 3（版本线续接 0.3.x）、[0003](2026-10-29-candidate-list-replaces-allowlist.md) 决策 4（bump 0.3.2）

## 背景

- npm 上存在 0.3.0 包（2026-10-28 19:55 UTC，v0.3.0 tag 推送触发 release.yml；tag 事后被删、`latest` 被拨回 0.0.2，包体无法撤回）。该 tag 是误发：0.0.x 才是本插件的产品线（0.0.1/0.0.2 已发布），0.3.0 从未经过用户批准。
- 开发过程中我曾按"已发布版本之上续号"的机械 semver 推理，把本地迭代号定为 0.3.1/0.3.2 并主张在此线上续接——用户裁定该方向错误：不应在错误 tag 的后果上继续搭楼。

## 决策

1. **产品线固定 0.0.x 连续递增**：0.0.2 → 0.0.3 → …。npm 孤儿包 0.3.0 不属于本线；禁止以 0.3.x/任何 0.x>0 形式发布。安装侧无实际冲突：`latest` 链沿 0.0.2 → 0.0.3 前移，`^0.0.2` 区间消费者正常解析 0.0.3；显式装过 0.3.0 的个别环境按卸载重装处理。
2. **版本号只在发布时推进**：一个细节完善/一轮打磨 ≠ 一次版本更新（用户指令）。日常轮次用规范 commit 管理；本地 tarball 迭代复用当前版本号，重装走同版本 force 流程（AGENTS.md）。仅当用户人工实测门通过并明确同意发布时，才一次性 bump → CHANGELOG 定稿 → 附注 tag。
3. **守卫**：`tests/manifest.spec.ts` 断言版本匹配 `0.0.x` 且高于 0.0.2（取代原"不低于 0.3.0"守卫）；CHANGELOG 顶部条目与版本 lockstep 守卫保留。
4. **历史口径**：CHANGELOG v0.0.3 条目如实记录 0.3.0 孤儿包事实与 0.3.1/0.3.2 本地迭代号并入过程；ADR 0002/0003 中与此冲突的版本线条款被本决策取代（原文不回改）。

## 影响

- 当前发布候选为 **v0.0.3**（官方子智能体全面接管 + 完整替代 + 打磨），等待用户人工实测门批准后才打 tag 推送。
- release.yml 发布 0.0.3 时 npm `latest` 将从 0.0.2 前移至 0.0.3；孤儿包 0.3.0 留置注册表，如需标注由用户另行决定（deprecate 等）。
